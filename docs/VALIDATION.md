# Проверки и план эксперимента

## Что проверяется программно

`pytest` (79 тестов: ядро, интерфейс, запуск в Colab) проверяет: геометрию площадки и правило трёх очков для NBA и FIBA, восстановление метров по ключевым точкам и отказ вырожденной гомографии, детектор монтажных склеек, кластеризацию команд и голосование по трекам, привязку номеров с отбрасыванием неоднозначных случаев, разбор составов и сопоставление кластеров с командами, скорость/дистанцию на известном движении и игнорирование дрожания, отбрасывание телепортов и разрывов, владение по классу детектора и по близости мяча, набор владения в плотной игре при мяче в каждом третьем кадре, отсутствие владения у летящего мяча, сохранение владения при спорной близости, сведение дубликатов треков SAM2 и переподачу промптов только там, где трека нет, автомат броска (старт/попадание/промах), сохранение позиции игрока в момент выпуска для 2/3 очков, попадание при пропусках детекции мяча между точками над и под ободом, различение перехвата и потери по «мёртвому мячу», передачу и результативную передачу, подбор в защите, отсутствие выдуманного промаха, ввод мяча после попадания вместо потери, штрафной за 1 очко, объединение треков одного игрока в box score и игнорирование отклонённых событий, чтение табло, миграцию конфигураций версии 0.1, ключ кэша восприятия, отказ незавершённого кэша.

Также проверяется перевод в метры, отказ вырожденной калибровки, скорость/дистанцию на известном движении, отсутствие пути через пропуски, неизвестные метры, владение с задержкой подтверждения, кандидатов событий, отсутствие выдуманного промаха, повторное попадание, чтение счёта, временные единицы, формат запроса Roboflow без настоящего ключа, сохранение исходных данных после проверки, отмену и экспорт частичного результата, построение интерфейса, синтаксис Colab.

Сквозной тест обрабатывает `examples/demo.mp4`: 15 с, 30 исходных FPS, 15 анализируемых FPS, площадка NBA сверху, четыре игрока, судья, мяч и табло. Сценарий записан в `examples/demo_truth.json`: девять событий (передача, потеря, перехват, передача, бросок из-за дуги, попадание, результативная передача, бросок из-под кольца, подбор в защите), счёт 0:3 и точные дистанции каждого игрока. Тесты требуют precision = recall = 1 по всем видам событий (допуск ±1.2 с), совпадения счёта, правильных имён из составов и дистанций с точностью 20 %. Реальный Tesseract читает нарисованное табло и должен получить 0:3 независимо от счёта по броскам.

Демо специально содержит трудные случаи: разрыв трека (игрок получает новый ID, но объединяется по номеру), судья, которого нельзя учитывать как игрока, две ключевые точки площадки с низкой уверенностью и шум рамок ±0.8 пикселя. Это проверка интеграции и арифметики; детекция нейросетью в этом тесте не участвует.

`scripts/verify_real_inference.py` отдельно скачивает штатное фотографическое изображение `bus.jpg` Ultralytics, запускает настоящую YOLO11n и проводит её результат через видео и ByteTrack. Требуется интернет для изображения и весов. Это проверка установленной модели, не баскетбольной точности.

Фактический протокол сборки приложен в `docs/BUILD_VERIFICATION.json`. Запуск на физической RTX 3050 / Colab GPU и качество на пользовательском матче не подтверждаются тестом CPU. Скорость синтетического демо нельзя выдавать за FPS работы нейросети.

## Как провести исследование для диплома

1. Собрать несколько матчей / камер с правом использования. Разделить train/validation/test **по матчам**, чтобы соседние кадры одного эпизода не попадали в разные выборки.
2. Разметить игроков, мяч, кольца и действия; отдельно — время и участников событий. Для теста не подбирать пороги по его разметке.
3. На коротких фрагментах вручную задать составы и соответствие ID реальным игрокам. Считать количество смен ID, IDF1/HOTA только при наличии покадровой разметки личности и подходящего отдельного оценщика.
4. Оценить детекцию игроков и мяча раздельно: precision/recall, mAP@0.5 и mAP@0.5:0.95, recall маленького мяча. Этот проект сам не вычисляет mAP без размеченного detection dataset.
5. Оценить события по временным меткам. Для каждого вида: TP/FP/FN, precision, recall, F1, заранее выбрать допуск, например ±1 с. Один прогноз может соответствовать только одному эталонному событию.
6. Для скорости/дистанции использовать независимый эталон: размеченные перемещения по известным линиям или измеренные траектории. Считать MAE/RMSE и покрытие действующими измерениями. Самооценка по той же гомографии не является независимой проверкой.
7. Владение: вручную размеченные интервалы, MAE секунд на игрока, доля кадров с правильным владельцем и доля «неизвестно». Табло: доля точных пар A:B и задержка принятия изменений.
8. Производительность: модель, устройство, разрешение, FPS анализа, длина ролика, wall time, максимальная VRAM/RAM. Измерять отдельно холодный запуск и обработку после загрузки модели.

Минимальная ручная разметка событий — CSV с `time_s,kind,player_id`. В ней `kind` использует `shot`, `made`, `steal`, `turnover`, `pass`, `assist`, `rebound_off`, `rebound_def`, `block`, `score_change` по нужным категориям. Сравнивайте только категории, для которых размечен весь проверяемый фрагмент.

```bash
.venv/bin/python scripts/evaluate_events.py outputs/run-.../events.csv ground_truth.csv --tolerance 1
```

Суффикс `_candidate` автоматически снимается перед сравнением. Отклонённые прогнозы не учитываются. По умолчанию сопоставление по виду и времени; `--match-player` допустим только после согласования ID с эталоном. Скрипт выдаёт JSON метрик. Нулевое число эталонов/предсказаний даёт `null` для неопределённых отношений, а не выдуманные 100%.

## Границы заявлений

Функциональность прототипа не означает достигнутую точность на произвольной телетрансляции. Полный матч содержит повторы, крупные планы, склейки, скрытый мяч и смену игроков. Версия 0.2 ориентирована на отдельные игровые фрагменты одной камеры; при обработке полного матча часть данных будет отсутствовать либо нуждаться в проверке.

## Сравнение трекеров (ByteTrack и SAM2)

Оба трекера работают в одном конвейере при прочих равных, поэтому сравнение
корректно: различается только этап отслеживания.

```bash
.venv/bin/python scripts/compare_configs.py match.mp4 --seconds 30 --players 10 \
    --config "ByteTrack:tracker=bytetrack" --config "SAM2:tracker=sam2"
```

Показатели без ручной разметки (считаются автоматически из `tracks.csv`):

| Метрика | Что означает | Куда стремиться |
|---|---|---|
| `fragmentation` | треков на одного игрока | 1.0 |
| `mean_track_s` | средняя длительность трека | к длине фрагмента |
| `short_share` | доля треков короче секунды | 0 |
| `coverage` | сколько игроков ведётся одновременно | 1.0 |
| `identified` | сколько треков получили номер | число игроков |

С покадровой разметкой личностей (`time_s, player, x_px, y_px`) добавляются
IDF1 и число подмен идентификаторов: `--reference identities.csv`. Размечать
достаточно 10–15 секунд, отмечая положение каждого игрока раз в полсекунды.

Полноценные HOTA и MOTA считаются внешним оценщиком (TrackEval) по разметке в
формате MOT; в проекте они не вычисляются, чтобы не заявлять непроверенных
цифр.

## Сравнение моделей чтения номеров

Обе модели решают одну задачу и сравниваются на одном фрагменте:

```bash
.venv/bin/python scripts/compare_configs.py match.mp4 --seconds 30 --players 10 \
    --config "SmolVLM2:number_reader=smolvlm" --config "ResNet:number_reader=resnet"
```

Показатели: `identified_tracks` (сколько треков получили номер), `number_crops_read`
(сколько изображений прочитано), общее время обработки. Точность самой модели
берётся из отчёта обучения `models/jersey_resnet_report.json`: доля верных
ответов на отложенной выборке и список самых частых путаниц между цифрами.

Для честного сравнения точности на своих данных разметьте 50–100 кропов
номеров из собственной записи и прогоните обе модели на них: цифры Roboflow
(86 % и 93 %) получены на кадрах плей-офф НБА и к другой съёмке не переносятся.

## Сравнение конфигураций (для главы с экспериментами)

Один и тот же фрагмент прогоняется в трёх режимах и сравнивается по одинаковым метрикам:

| Режим | Как запустить | Что показывает |
|---|---|---|
| Базовая линия COCO | `--backend yolo` с `yolo11n.pt` | предел универсальной модели: мяч и действия почти не находятся |
| Модели Roboflow | `--backend roboflow` | что даёт обучение на баскетбольных данных |
| Свои дообученные веса | `--backend yolo` с путём к своим весам | эффект адаптации к собственной съёмке |

Показатели для таблицы берутся из `summary.json`: `ball_detection_fraction`, `calibrated_frame_fraction`, `calibration_quality.mean_reprojection_error_m`, `track_count`, `identified_tracks`, `event_count`, `wall_seconds`; метрики событий — из `scripts/evaluate_events.py`.
